# Reporte de cambios del proyecto Joper / Nexxo

**Periodo:** 23 de julio de 2026 al 4 de septiembre de 2026  
**Último commit disponible:** `5fb6038` — 3 de septiembre de 2026  
**Rama revisada:** `main`  
**Fuente:** historial de Git del repositorio

## 1. Resumen ejecutivo

Durante el periodo revisado se registraron **69 commits**. El historial incluye cambios de aplicación, migraciones, pruebas, documentación técnica, logs operativos y capturas de referencia.

Los cambios funcionales más importantes fueron:

1. Mejoras en estados de cuenta, pedidos y embarques.
2. Implementación y refinamiento del módulo de producción.
3. Adaptación de cotizaciones para Joper USA:
   - USD como moneda predeterminada.
   - impuesto de venta manual y editable.
   - configuración inicial de pallets.
   - cálculos y PDFs diferenciados por compañía.
4. Configuración independiente de Microsip por compañía y soporte para compañías hijas.
5. Correcciones de autenticación, timeouts y concurrencia de Firebird.
6. Mejor aislamiento entre tenants, empresas, usuarios y notificaciones.
7. Recordatorios de visitas programadas y mejoras en check-ins.
8. Ocultamiento de visitas canceladas en la vista normal, conservándolas para historial.
9. Validación de compilación y pruebas automatizadas; al cierre del periodo, la suite ejecutada reportó **98 pruebas aprobadas**.

### 2.5 Microsip y Firebird

El 31 de agosto y el 1 de septiembre se concentró un bloque importante de trabajo en conexiones Microsip/Firebird.

#### Configuración y pruebas de compañías

- Se permitió probar una nueva conexión con los valores todavía no guardados en el formulario.
- Las compañías hijas pueden recibir una copia editable de la configuración Microsip del padre.
- La configuración de cada compañía se maneja de forma independiente.
- Las pruebas de conexión ya no deben alterar de forma permanente la configuración de compañías existentes.

#### Autenticación Firebird

Se probaron y ajustaron los mecanismos de autenticación Firebird para soportar las instalaciones reales:

- SRP.
- Legacy authentication.
- Compatibilidad con servidores que envían paquetes de continuación.
- Ajustes de WireCrypt según la compatibilidad del cliente `node-firebird`.

El historial muestra que se probaron varias combinaciones y finalmente se conservaron las que permiten conectar tanto compañías existentes como compañías nuevas.

#### Timeouts, concurrencia y archivos `.fdb`

- El timeout del attach comienza después de adquirir el bloqueo global de handshake.
- Un attach bloqueado no debe detener a las demás compañías.
- Se evitó abrir simultáneamente el mismo archivo `.fdb` para varios tenants.
- Se espera el detach antes de permitir otro sync sobre el mismo archivo.
- Se agregaron reintentos y limpieza de workers residuales.
- Se experimentó con un worker separado para aislar un handshake bloqueado; posteriormente se restauró el attach en proceso para evitar respuestas 504 en el flujo estable.
- La sincronización de productos se aceleró evitando operaciones innecesarias por cada registro.
- Se agregó un parche de autenticación para el paquete `node-firebird`.

Commits principales:

- `7259292`, `0c30332`, `2120fc7` — timeouts, bloqueos y aislamiento de attaches.
- `a48c76d`, `7311d7b`, `18233a8`, `4ffe77f`, `3de6891` — autenticación y WireCrypt.

### 2.9 Producción

El 3 de septiembre se implementó y refinó la administración de equipos en producción.

- Los administradores pueden agregar equipos a un pedido.
- Pueden quitar equipos.
- Pueden cambiar cantidades.
- El endpoint protegido es `PUT /api/orders/:id/equipment`.
- Solo se permite modificar pedidos en estados editables.
- No se permite modificar equipos después de liberaciones, embarques o estados terminales.
- Se recalculan subtotal, impuesto, descuentos y total de la cotización asociada.
- Se conserva el aislamiento por tenant y empresa.
- La interfaz muestra edición dentro del detalle del pedido.
- Se corrigió un caso de datos históricos donde un pedido ya tenía dos renglones del mismo producto.
- Los duplicados históricos pueden conservarse y editarse.
- Un producto nuevo no puede agregarse repetido en el mismo pedido.

Commits principales:

### Observación de despliegue

Los logs agregados al repositorio muestran una incidencia operativa durante el despliegue en VPS:

- La compilación terminó correctamente.
- `npm` reportó advertencias de peer dependencies y vulnerabilidades.
- El despliegue falló al ejecutar `pg_dump`/`psql` con el usuario Linux `root`.
- La causa observada fue usar un valor de ejemplo para `DATABASE_URL` en lugar de la URL real de PostgreSQL.
- La aplicación debe desplegarse con la URL real o dejando que el script la tome de `ecosystem.config.js`.

## 6. Riesgos y recomendaciones

1. **Revisar el archivo de credenciales agregado en `d4acccb`.**  
   El commit se titula “Attach database connection credentials file”. Si el archivo contiene credenciales reales, debe retirarse del repositorio, revocarse o rotarse la contraseña y verificarse el historial remoto.

2. **Corregir el reporte de éxito del backup VPS.**  
   Los logs muestran que `pg_dump` falló, pero el script continuó informando que el backup había terminado. El script debería usar `pipefail` y marcar el backup como fallido de forma inequívoca.

3. **Revisar las 35 vulnerabilidades reportadas por npm.**  
   No se debe ejecutar `npm audit fix --force` sin revisar cambios potencialmente incompatibles.

4. **Reducir el tamaño del bundle.**  
   El build funciona, pero conviene evaluar code splitting o `manualChunks` para mejorar carga inicial.

5. **Agregar pruebas específicas para producción.**  
   La funcionalidad de equipos tiene validación en cliente y servidor; conviene agregar pruebas de ruta que cubran:
   - edición de cantidades;
   - eliminación;
   - alta de equipos;
   - rechazo de pedidos con liberaciones;
   - conservación de duplicados históricos;
   - rechazo de duplicados nuevos.
